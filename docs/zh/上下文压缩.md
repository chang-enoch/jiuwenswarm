# 上下文压缩

## 1. 概念科普

### 1.1 上下文的概念

在 AI 对话系统中，**上下文**指的是对话过程中产生的所有历史信息，包括用户的提问、AI 的回答、工具调用的结果等。这些信息共同构成了 AI 理解当前对话状态和提供准确回答的基础。

### 1.2 上下文窗口限制

尽管上下文对于 AI 理解对话至关重要，但所有 AI 模型都存在**上下文窗口限制**——即模型在单轮对话中能够处理的最大信息量（通常以 Token 数量衡量）。当对话超出这个限制时，AI 会出现以下问题：

- 响应速度显著变慢
- 早期关键信息被遗忘
- 回答准确性下降
- 系统资源消耗过大

### 1.3 上下文压缩的概念

**上下文压缩**是一种智能优化技术，通过对历史对话内容进行分析、筛选和精简，在保持对话连贯性的前提下，将上下文信息压缩到模型可处理的范围内。

其核心思想可以类比为：在阅读一本长篇小说时，我们不需要记住每一个细节，只需要记住关键情节和人物关系，就能理解故事的发展。

JiuwenSwarm 可以通过上下文压缩卸载机制，使用 `[[OFFLOAD:...]]` 格式的索引标记大工具消息的卸载内容，在显著减少上下文数据量的同时，保留大工具消息的检索能力。

> **注意**：普通压缩后的内容无法召回，只有被卸载的大工具消息内容可以通过 `[[OFFLOAD:...]]` 索引标记进行检索。

### 1.4 应用场景

上下文压缩技术适用于各种需要长时间对话的场景：

- **数据分析**：处理大量数据表格和分析结果
- **项目管理**：跨多天的项目跟进和讨论
- **代码开发**：长时间的代码编写和调试
- **文档创作**：长篇文档的协作编写
- **客户支持**：复杂问题的长时间解决过程

## 2. 基础使用

### 2.1 开启上下文压缩

上下文压缩功能默认是关闭的，您可以通过以下方式开启：

**方式一：通过配置文件开启**

编辑 `config.yaml` 配置文件，找到 `context_engine_config` 部分：

```yaml
    enabled: true         # 将此设置为 true 开启上下文压缩
```

**方式二：通过前端界面开启**

在 JiuwenSwarm 客户端中，进入页面：

![上下文压缩设置](../assets/images/current-ui/25-配置信息-其他配置-详情.png)

- 点击左侧菜单栏的"配置信息"
- 选择"其他配置"
- 找到"上下文压缩"
- 点击开关将其开启

### 2.2 查看上下文压缩状态

开启上下文压缩后，您可以通过以下方式查看压缩状态：

**方式一：查看对话状态面板**

在对话界面的右下角，系统会实时显示上下文窗口的使用情况：

![上下文压缩状态面板](../assets/images/current-ui/10-工作页面-完整.png)

状态面板包含以下信息：

- 当前使用的 Token 数
- 模型支持的最大 Token 数
- 当前占用比例

**方式二：通过 Slash 命令查看**

在对话输入框中输入以下命令可以查看详细的上下文压缩信息：

```bash
/context
```

![上下文状态面板](../assets/images/current-ui/10-工作页面-完整.png)

## 3. 案例实践

为便于演示上下文压缩效果，本案例将触发阈值调整为 40K（默认值为 100K）。当上下文长度达到 40K 时，系统自动触发压缩机制，可在较短对话中观察压缩过程。

开发者可根据接入模型和业务需求，通过修改 `config.yaml` 中各处理器的触发阈值参数自定义阈值（默认按上下文占比 `trigger_context_ratio` 触发，也可用 `trigger_token_threshold` 固定为绝对 Token 触发，详见第 5 章）。

### 3.1 无上下文压缩的情况

**场景**：用户与 AI 咨询北京3天旅行计划（单一请求）

**对话过程**：

```

Assistant: 好的，我来为您规划一个详细的北京3天旅行计划。

【北京3天深度游行程】

Day 1: 天安门广场 → 故宫 → 景山公园
- 上午：天安门广场看升旗
- 中午：故宫游览
- 下午：景山公园俯瞰故宫全景

Day 2: 八达岭长城 → 明十三陵
- 上午：八达岭长城
- 下午：明十三陵

Day 3: 颐和园 → 圆明园 → 南锣鼓巷
- 上午：颐和园
- 中午：圆明园
- 下午：南锣鼓巷感受老北京文化
```

**说明**：

- 图片中可看到：AI回复内容包含丰富的旅行信息

- Token消耗主要来自：AI的详细回复内容 + 工具调用返回的数据

**最终结果**：

- 整个对话的上下文 Token 数已达到 41.3K，占用模型窗口的 20.6%
- 后续对话风险：如果用户继续追问细节或请求扩展计划，上下文会继续增长
- 潜在问题：随着对话深入，可能接近模型上下文窗口上限

### 3.3 实际效果说明

从两张示例图片的实际数据来看（基于40k阈值测试）：

2. **系统功能表现**：
   - 两种场景均成功完成了旅行计划生成
   - 有压缩场景额外支持了技能创建等扩展功能
   - 内存占用稳定在362MB左右，系统资源消耗差异不明显
3. **实际价值体现**：
   - 上下文压缩通过优化信息结构，使系统能够更好地处理后续扩展请求
   - 保持核心信息完整性的同时，提升了系统的功能扩展性
4. **阈值说明**：
   - 当前示例基于40k Token触发阈值测试，便于快速观察压缩效果
   - 生产环境中可根据实际需求调整阈值参数（如100k及以上）

## 4. 特性解读

### 4.1 动态触发机制

上下文压缩不是固定的预处理步骤，而是根据对话状态动态触发的智能优化：

- **基于上下文占比**：当上下文（含系统提示词 + 工具定义 + 消息）达到窗口容量的 `trigger_context_ratio` 比例时触发
- **基于绝对 Token**：配置 `trigger_token_threshold` 后，改为上下文达到该绝对 Token 数时触发（优先于占比标准）
- **按需保留**：各压缩器通过 `keep_recent_messages` 保留最近若干条原始消息，保证上下文连续性
- **可配置性**：用户可以根据需要调整各个触发阈值（详见第 5 章）

### 4.2 智能识别和压缩

系统采用先进的自然语言处理技术，能够：

- **区分消息类型**：自动识别用户消息、AI 回答和工具结果
- **识别重要性**：基于语义分析判断消息的重要程度
- **选择压缩方式**：对不同类型的内容采用不同的压缩策略
  - 对工具返回的冗长数据进行摘要
  - 对重复信息进行合并
  - 对不重要的内容进行过滤

### 4.3 关键信息保护

上下文压缩不会丢失重要信息，系统会：

- **保留最近消息**：通过 `keep_recent_messages` 参数保留指定数量的最新原始消息
- **保留完整轮次**：压缩器会按工具边界对齐，避免拆散进行中的工具调用轮次
- **识别关键内容**：通过语义分析自动识别并保留关键信息

### 4.4 检索能力保持

上下文压缩不会破坏对话的检索能力：

- **卸载标记**：部分处理器使用 `[[OFFLOAD:...]]` 格式标记被卸载的内容，便于未来按需加载
- **关联保留**：压缩后的信息仍然与原始上下文保持关联
- **按需加载**：在需要时可以通过卸载标记按需加载原始信息

### 4.5 性能优化

上下文压缩能够显著提升系统性能：

- **减少内存占用**：将上下文数据量减少 50%-80%
- **提高响应速度**：降低模型推理时间，提升用户体验
- **支持更长对话**：突破模型上下文窗口限制，支持长时间对话
- **降低成本**：减少 Token 消耗，降低使用成本

## 5. 进阶配置

JiuwenSwarm 的上下文压缩由 openjiuwen 的 **forked（重构版）处理器**驱动，包含 4 个主要处理器 + 1 个可选的循环折叠处理器。配置通过 `react.context_engine_config` 下的 `xxx_config` 字典逐项透传，以下字段均与代码实际生效字段一致。

> ⚠️ 注意：旧版压缩器曾用 `tokens_threshold`、`compression_target_tokens`、`messages_to_keep`、`first_pass_target_tokens` 等字段，这些字段在重构版中**已失效**（会被静默忽略）。请以本文档与 `config.yaml` 中的字段为准。

### 5.1 完整配置示例（真实生效字段）

```yaml
context_engine_config:
  # 全局开关
  enabled: true                    # 启用上下文压缩（核心开关）
  enable_reload: true              # 启用重新加载
  enable_openrouter_model_context_window_tokens: true # 按模型自动解析上下文窗口大小

  # 1. 消息摘要卸载器 - 处理工具调用等特定类型消息
  message_summary_offloader_config:
    add_message_threshold_ratio: 0.1   # 新增消息处理的上下文占比阈值
    ttl_seconds: 300                   # TTL 空闲秒数
    ttl_context_occupancy_ratio: 0.5   # TTL 处理的上下文占比阈值
    ttl_message_threshold_ratio: 0.05  # 单次 TTL 处理的占比阈值

  # 2. 对话压缩器 - 压缩整个对话历史
  dialogue_compressor_config:
    trigger_context_ratio: 0.8        # 触发压缩的上下文占比
    min_target_context_ratio: 0.1     # 被压缩内容的最小占比下限
    trigger_token_threshold: 200000   # 可选：绝对 Token 触发（填了优先于比例）
    target_retention_ratio: 0.3       # 可选：压缩后保留约 30%

  # 3. 当前轮次压缩器 - 压缩当前对话轮次
  current_round_compressor_config:
    trigger_context_ratio: 0.8
    min_target_context_ratio: 0.1
    keep_recent_messages: 4           # 保留最近的原始消息数
    trigger_token_threshold: 200000
    target_retention_ratio: 0.3

  # 4. 轮次级别压缩器 - 多轮对话高级压缩
  round_level_compressor_config:
    trigger_context_ratio: 0.8
    min_target_context_ratio: 0.1
    keep_recent_messages: 4
    trigger_token_threshold: 200000
    target_retention_ratio: 0.3

  # 5. 循环折叠处理器（可选，默认关闭）
  reasoning_tool_loop_compact_config:
    enabled: false
```

### 5.2 配置参数说明

#### 消息摘要卸载器（message_summary_offloader_config）

| 参数 | 说明 | 默认值 |
|------|------|--------|
| `add_message_threshold_ratio` | 新增工具消息触发处理的上下文占比阈值 | 0.1 |
| `ttl_seconds` | 两次窗口请求间的空闲秒数（TTL 判定） | 300 |
| `ttl_context_occupancy_ratio` | TTL 处理的上下文占比阈值 | 0.5 |
| `ttl_message_threshold_ratio` | 单次 TTL 处理一条工具的占比阈值 | 0.05 |

#### 对话压缩器（dialogue_compressor_config）

| 参数 | 说明 | 默认值 |
|------|------|--------|
| `trigger_context_ratio` | 触发压缩的上下文占比（未填 `trigger_token_threshold` 时生效） | 0.8 |
| `min_target_context_ratio` | 被压缩内容的最小占比下限 | 0.1 |
| `trigger_token_threshold` | 可选：绝对 Token 触发阈值，填了优先于 `trigger_context_ratio` | 无（留空） |
| `target_retention_ratio` | 可选：压缩目标保留率（摘要 ≈ 被压缩内容 Token × 该比例） | 无（留空） |

#### 当前轮次压缩器（current_round_compressor_config）

| 参数 | 说明 | 默认值 |
|------|------|--------|
| `trigger_context_ratio` | 触发压缩的上下文占比（未填 `trigger_token_threshold` 时生效） | 0.8 |
| `min_target_context_ratio` | 被压缩内容的最小占比下限 | 0.1 |
| `keep_recent_messages` | 保留最近的原始消息数 | 0 |
| `trigger_token_threshold` | 可选：绝对 Token 触发阈值，填了优先于 `trigger_context_ratio` | 无（留空） |
| `target_retention_ratio` | 可选：压缩目标保留率 | 无（留空） |

#### 轮次级别压缩器（round_level_compressor_config）

| 参数 | 说明 | 默认值 |
|------|------|--------|
| `trigger_context_ratio` | 触发压缩的上下文占比（未填 `trigger_token_threshold` 时生效） | 0.8 |
| `min_target_context_ratio` | 被压缩内容的最小占比下限 | 0.1 |
| `keep_recent_messages` | 保留最近的原始消息数 | 4 |
| `trigger_token_threshold` | 可选：绝对 Token 触发阈值，填了优先于 `trigger_context_ratio` | 无（留空） |
| `target_retention_ratio` | 可选：压缩目标保留率 | 无（留空） |

#### 循环折叠处理器（reasoning_tool_loop_compact_config）

| 参数 | 说明 | 默认值 |
|------|------|--------|
| `enabled` | 是否启用循环折叠 | false |
| `consecutive_threshold` | reasoning + 工具名连续相同几轮触发折叠 | 3 |
| `tool_args_consecutive_threshold` | 工具名 + 入参连续相同几轮触发折叠 | 5 |
| `bailout_threshold` | reasoning 规则折叠次数达此值后终止 | 3 |
| `tool_args_bailout_threshold` | 工具入参规则折叠次数达此值后终止 | 2 |

### 5.3 绝对 Token 触发与压缩目标比例

三个压缩器（`dialogue_compressor_config`、`current_round_compressor_config`、`round_level_compressor_config`）新增两个可选参数：

- **`trigger_token_threshold`**：绝对 Token 触发阈值。填写后，只有当上下文（含系统提示词 + 工具定义 + 消息）token 达到该值时才压缩，**优先于** `trigger_context_ratio`；留空/注释则回退到比例标准触发。
- **`target_retention_ratio`**：压缩目标保留率。填写后，压缩摘要的目标长度 ≈ 被压缩内容 token × 该比例（例如 `0.3` = 压缩后保留约 30%），实现方式为给压缩模型追加长度指令并设置 `max_tokens` 上限；留空/注释则不控制输出长度，沿用默认行为。

> 两个参数均为可选，默认不填（`None`），行为与旧版本完全一致。

### 5.4 配置注意事项

1. **处理器独立工作**：各处理器各自独立触发，互不依赖
2. **阈值配置**：默认以「上下文占比」触发；如需固定按绝对 Token 触发，填写 `trigger_token_threshold`（如 `200000`）
3. **必填类型**：`trigger_context_ratio` / `min_target_context_ratio` 为 0~1 之间的小数；`target_retention_ratio` 填值时同样必须为 0~1 之间的小数
4. **多级压缩**：`round_level_compressor_config` 与 `current_round_compressor_config` 通过 `keep_recent_messages` 保留最近原始消息，平衡压缩收益与上下文连续性

通过合理配置这些参数，用户可以根据自己的使用场景和需求，获得最佳的上下文压缩效果和对话体验。
